# v2 Versioning (Phase 1)

Version fields are explicit and distinct in `v2` contracts.

## Version fields and meaning

- `contentSchemaVersion`
  - changes when content shape or validation semantics change.
- `contentVersion`
  - human-facing release identifier for a content set.
- `contentFingerprint`
  - deterministic SHA-256 hash of canonical serialized content for exact bundle identity.
- `scoringVersion`
  - changes when scoring semantics change.
- `responseSchemaVersion`
  - changes when response payload contract changes.
- `resultSchemaVersion`
  - changes when assessment result payload shape changes.
- `researchSchemaVersion`
  - changes when research envelope contract changes.

## Guardrails

- Fingerprint is derived from canonical serialized content bytes, not timestamps.
- A mismatch between provided version metadata and derived fingerprint indicates rejected/invalid canonicalization during runtime integration.

## Phase 2 content artifacts

The canonical source is the versioned `v2/content/` tree. Compilation produces
`v2/generated/content.bundle.json`, `v2/generated/content-manifest.json`, and a
machine-generated inventory in `docs/v2/generated/content-inventory.md`. The
compiler derives counts and the fingerprint from validated content and excludes
the self-referential fingerprint field from its hash input.

## Phase 4 result schema

Phase 4 changes resultSchemaVersion to result-v2.phase4.1 because construct
results are now a discriminated scored/abstained union with explicit
numerator, denominator, evidence, support, uncertainty, and abstention
reason fields. The content fingerprint is regenerated by the compiler after
this metadata change. The scoring version remains the measurement-contract
version because Phase 4 implements the already-approved construct formula
rather than changing it.

## Phase 5 result schema

Phase 5 changes resultSchemaVersion to result-v2.phase5.1 because primary
profile results are now explicit scored/abstained unions with comparison
evidence, typed gate evaluations, distance/similarity, deterministic rank and
tie-group fields, and profile-level uncertainty. The scoring version remains
the measurement-contract version: Phase 5 consumes Phase 4 construct scores
and does not change item or construct arithmetic.
## Phase 6 version increments

The modifier content contract adds explicit `fitThreshold` metadata for
ordinary core modifiers, so the source manifest advances to
`content-schema-v2.phase6.1`. Modifier scoring is versioned as
`scoring-v2.phase6.1` and its public result contract as `result-v2.phase6.1`.
The content version remains the approved v1-derived registry version; the
compiled fingerprint changes because the canonical metadata and modifier
content contract changed.

## Phase 9 result schema

The unified `AssessmentResult` increments the result contract to
`result-v2.phase9.1`. The content, response, and scoring versions remain bound
to their existing Phase 8, Phase 1, and Phase 7 contracts. A scorer rejects a
bundle with an unsupported result schema rather than silently projecting it.

## Phase 12 persistence versions

Private persistence uses `save-v2.phase12.1` and public result sharing uses
`share-v2.phase12.1`. These schemas are separate from content, response,
scoring, and result versions. A content fingerprint or response-contract
mismatch is incompatible; a scoring/content-version change requires replay.
The save and share digests are integrity checks over canonical bytes and are
not authentication tokens.

## Research Phase 13 versions

Research infrastructure accepts only `research-v2.phase13.1`, `research-protocol-v2.phase13.1`, and `consent-v2.phase13.1`, bound to the current content, response, scoring, and result versions and the Phase 12 content fingerprint. These are research acceptance versions, not scoring versions.
